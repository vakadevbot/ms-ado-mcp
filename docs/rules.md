# Контракт приватных правил

`ADO_RULES_FILE` — путь к доверенному Python-модулю. Он импортируется при запуске,
экспортирует непустой список/кортеж `PROJECTS` с уникальными именами проектов.
`AZURE_DEVOPS_PROJECT`, если задан, должен входить в список.
Имя проекта — точное отображаемое имя Azure, не GUID.

```python
from ms_ado_mcp.models import Violation
from ms_ado_mcp.policy import BoardScope, ProjectPolicy, Rule


def check_owner(item, context):
    if not item.fields.get("System.AssignedTo"):
        return [
            Violation(
                code="owner.required",
                message="Укажите ответственного.",
                field="System.AssignedTo",
            )
        ]
    return []


PROJECTS = [
    ProjectPolicy(
        name="Your Project",
        write_scope=BoardScope(area_path="Your Project\\Your Team"),
        rules=(
            Rule(
                code="owner",
                instructions="У каждого work item должен быть ответственный в System.AssignedTo.",
                check=check_owner,
            ),
        ),
    ),
]
```

Это пример API расширения, не готовый корпоративный регламент.

## ProjectPolicy

| Поле | Смысл |
| --- | --- |
| `name` | Имя разрешённого проекта |
| `work_item_types` | Сопоставление логического типа с именем в Azure |
| `active_categories` | Категории активных состояний; по умолчанию `("InProgress",)` |
| `active_states` | Точные состояния по логическому типу; приоритет над категориями |
| `defaults` | Поля черновика по типам, например `{"task": {"System.AreaPath": "Project\\Team"}}` |
| `guidance` | Дополнительные инструкции для ИИ |
| `rules` | Кортеж объектов `Rule` |
| `write_scope` | `BoardScope` с точным Area Path и необязательной итерацией; без него запись запрещена |

Списки/поиск ограничены настроенными типами. Чтение отдельного work item и
его родителя допускает другие типы внутри проекта (например Epic).
Для проверки неизвестного типа потребуется добавить его поддержку в `Kind` и сервис.

Для записи разрешён ровно один проект с `write_scope=BoardScope(...)`.
Проект, область и итерацию нельзя выбирать в параметрах инструментов записи.
`BoardScope.area_path` (и, если задан, `iteration_path`) должны начинаться с имени
проекта и совпадать с полями элемента точно, без разрешения дочерних областей.
Для досок с общими областями эта проверка не означает уникальную визуальную доску.
Корпоративные значения задавайте только локально в приватном модуле.

Переопределения обычных полей от клиента применяются поверх `defaults`, затем выполняются
проверки. Для жёстко заданного обычного значения напишите проверку равенства: `defaults` —
удобное заполнение, а не запрет на изменение.
Исключение — область, итерация и поля колонок/дорожек доски: клиенту запрещено
их передавать, сервер подставляет область и настроенную итерацию из `BoardScope`.
Значения этих полей из `defaults` игнорируются.
Системные идентификаторы, тип, проект, родитель, title и description нельзя
передавать через дополнительные `fields`.

## Rule

`check(item, context) -> list[Violation]` или `async def check(...)`.
Пустой список означает успех. `None`, исключение и некорректный тип результата —
ошибка проверки, блокирующая создание. `severity="warning"` не блокирует,
по умолчанию используется `"error"`.

- `item.fields` содержит поля по reference name; значения могут быть строками,
  числами, JSON-объектами (например identity) и `null`.
- `item.id` / `item.rev` присутствуют при проверке существующей записи.
- `context.kind` — `user_story`, `task`, `feature` или `pi_goal`.
- `context.scope` — `draft` либо `existing`.
- `context.parents` / `context.children` — кортежи связанных work items со всеми полями.
- `context.project` — выбранный проект.
- `Rule.kinds` ограничивает применимость правила; по умолчанию все четыре типа.

Проверки получают отдельные копии элемента и контекста: мутации не исправляют
черновик и не влияют на последующие правила. Формируйте замечания и дайте ИИ
подготовить исправленные поля. Проверки должны быть детерминированными и не иметь
побочных эффектов; `async` полезен для чтения дополнительных корпоративных данных.
В stderr не выводите PAT и содержимое конфиденциальных документов.

`instructions` должен описывать то же условие, что `check`. Генерация промптов
из объектов Rule устраняет отдельный список инструкций, но соответствие текста коду
проверяет автор правила. Напишите в приватном репозитории тесты на допустимые
и недопустимые примеры, отдельно для `draft` и `existing`.

Встроенные проверки: непустой заголовок не длиннее 255 символов, не более одного
родителя, применимые корпоративные правила. Все связанные элементы должны быть
доступны в том же проекте; ошибки чтения не превращаются в успешную валидацию.
При создании все проверки повторяются непосредственно перед POST, без
`bypassRules`. Общей транзакции между чтением родителей и созданием в REST API нет.

`update_work_item` допускает только Task/User Story в фиксированной области,
не принимает проект/доску или произвольный JSON Patch. В `context.scope="existing"`
правила получают предлагаемый изменённый элемент, с сохранёнными полями и связями.
Без применимых правил или при ошибке проверки PATCH не выполняется.
Изменение содержит `test /rev` для защиты от конкурентного редактирования и
перемещения: ревизия берётся из того же чтения, по которому проверены границы.
Features и другие типы изменять нельзя, создавать их также нельзя.
